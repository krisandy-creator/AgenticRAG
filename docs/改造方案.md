# 目标
MySQL 管业务状态，ES 管全文召回，Milvus 管向量召回，OSS 管原文与解析产物，RAG 服务只做编排与融合。

# 目标架构
上传文档
-> OSS 保存原文件
-> Parse Worker 解析为标准 chunk
-> MySQL 记录 document / parse_job / index_job / chunk_manifest
-> ES 写入 chunk 全文索引
-> Milvus 写入 chunk embedding
-> 文档状态 ready

提问
-> query rewrite
-> ES BM25 召回
-> Milvus dense vector 召回
-> RRF/加权融合
-> hydrate chunk 内容与元数据
-> rerank
-> evidence selection
-> LLM answer + citations
-> Trace

# 改造方案

现在 services.py 同时负责 embedding、MySQL chunk 写入、Milvus 写入、本地 BM25、向量召回、融合打分。生产化应拆成：
ChunkIndexWriter
DenseVectorStore / MilvusVectorStore
SparseSearchStore / ElasticsearchStore
HybridRetriever
CandidateFusionService
ChunkHydrator

document_chunk.content 不应再做全文召回主数据
[entities.py (line 12)](D:/agent/RAG/OmniAgent/src/backend/agentchat/domains/indexing/entities.py:12) 当前把 chunk content 存 MySQL。生产态可以保留 chunk_manifest 或短 preview，但全文检索语料应进入 ES。MySQL 存 chunk_id/document_id/page_no/vector_id/content_hash/index_version/status 就够。

本地 BM25 逻辑应删除
[services.py (line 377)](D:/agent/RAG/OmniAgent/src/backend/agentchat/domains/indexing/services.py:377) 的 _bm25_scores 可以直接废弃。ES 返回的 _score 才是关键词召回分数。

Milvus Lite 与文件锁应彻底移除
[milvus_store.py (line 170)](D:/agent/RAG/OmniAgent/src/backend/agentchat/infrastructure/vector_store/milvus_store.py:170) 的 Lite short session、文件锁、.rag_storage 都是 MVP 代码。目标态只保留远程 Milvus client，配置用 uri/token/collection_name/metric_type。

ES 现在只是“配置残留”
[es_index.py (line 1)](D:/agent/RAG/OmniAgent/src/backend/agentchat/config/es_index.py:1) 没有调用链。要新增真正的 ElasticsearchChunkStore：ensure_index、upsert_chunks、delete_by_document、search。

## 检索层建议
不要继续手写线性加权一把梭。更生产的方式是：
ES top 100
Milvus top 100
-> RRF 融合到 top 50
-> rerank top 20
-> evidence selector top 6~8

RRF 比现在的归一化加权更稳，因为 ES 分数和向量分数不是同一量纲。后面如果要调优，再把 RRF、metadata boost、权限过滤、rerank 分数放进 trace。
